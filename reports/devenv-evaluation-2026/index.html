devenv.sh for HyperIDE

Can Nix-based environments help a bun + oxc/tsgo + docker-e2e monorepo — and is adoption worth it?
Date: June 3, 2026 Method: deep-research harness Sources: 22 (mostly primary) Claims: 25 verified → 23 confirmed, 2 refuted Verification: 3-vote adversarial

TL;DR. devenv.sh is a declarative, reproducible developer-environment manager built on Nix. For HyperIDE it genuinely covers four things: (1) a single environment with first-class bun support, (2) a built-in native Rust process manager (devenv 2.0) for orchestrating dev servers and e2e services, (3) a tasks DAG with content-aware incremental caching for monorepo builds, and (4) declarative git-hooks with a ready-made oxfmt hook and the same definitions in CI via a single devenv test. The price: a hard dependency on Nix (an onboarding cost for the whole team), partial loss of reproducibility on macOS, and fresh, not-yet-settled 2.0 subsystems. Verdict: a scoped pilot is justified; a wholesale migration is not.

1. What it is and how it works

devenv (repo cachix/devenv) is a manager of "fast, declarative, reproducible and composable" development environments built on top of Nix. It exposes 100,000+ Nixpkgs packages for Linux and macOS, x64 and ARM64 (including WSL2). devenv 2.0 (March 2026) is positioned as "a fresh interface to Nix": it keeps Nix's reproducibility guarantees while removing most of its day-to-day friction.

An environment is scaffolded with devenv init, which creates three files:

  • devenv.nix — the main declarative description: packages, env vars, languages, processes, services, tasks, git-hooks;
  • devenv.yaml — inputs (Nixpkgs sources) and imports, including monorepo imports;
  • .gitignore — ignores build artifacts (.devenv/).

Key architectural fact: a hard dependency on Nix. Installation is two-step — first Nix (the official installer or Determinate Systems' nix-installer), then devenv itself via nix profile install nixpkgs#devenv. There is no standalone, Nix-free binary. Even the Docker variant runs Nix inside the container. This means: adopting devenv = adopting Nix for every developer and in CI. This is the main cost line, and it is organizational, not technical.

2. Subsystems relevant to HyperIDE

2.1 Environment & first-class bun confirmed 3-0

devenv knows about bun at the language-module level. Enabling it is fully declarative:

# devenv.nix
{
  languages.javascript.enable = true;
  languages.javascript.bun.enable = true;          # installs bun from Nixpkgs
  languages.javascript.bun.install.enable = true;  # bun install on env entry
}

The implementation (src/modules/languages/javascript.nix) is version-aware: for bun ≥ 1.2 it uses --save-text-lockfile, and the bun install run is gated by a checksum of the lockfile + Node version so it doesn't re-install needlessly. For HyperIDE, which sits entirely on bun, this means the bun version stops being "whatever is in your PATH" and gets pinned in the repo.

2.2 Built-in Rust process manager confirmed 3-0

devenv 2.0 introduced its own native Rust process manager, replacing the external process-compose. Capabilities:

  • Supervision + dependency ordering via before/after;
  • Restart policies — on_failure / always / never;
  • Readiness probes — exec, HTTP, systemd notify;
  • Socket activation for zero-downtime restarts;
  • Watchdog heartbeats and file watching with auto-restart on file change;
  • Automatic free-port allocation (disable with --strict-ports).
# processes are declared right in devenv.nix
processes.devserver = {
  exec = "bun run scripts/dev.ts";
};
# start: devenv up   ·   stop: devenv processes down / devenv down

This is a direct replacement for HyperIDE's ad-hoc dev-server orchestration (currently bun install && bun run scripts/dev.ts) and for chaining dependent e2e services. Readiness probes (an HTTP probe on "compiled successfully") aim squarely at the project's known pain around waiting for dev-server readiness.

Caution: detached teardown. Open issues #1210 / #1597 report edge-case bugs stopping background services under devenv up -d, and #2484 covers a port-allocation edge case. The feature exists, but the reliability of clean teardown for detached processes is in question. For a CI/e2e pipeline that relies on a guaranteed shutdown of background services, this is critical — verify in a pilot.

2.3 Services confirmed 2-1

Services are a higher-level abstraction over processes: ~48 pre-configured ones (PostgreSQL, Redis, MongoDB, Kafka, MySQL, Elasticsearch, RabbitMQ, etc.) with ready-made interfaces (e.g. services.postgres.initialDatabases). HyperIDE gets little direct value from DB services — it isn't on a classic DB stack — but the mechanism is useful if e2e ever needs to spin up auxiliary backends locally without Docker.

2.4 Tasks: a DAG with incremental caching confirmed 3-0

Tasks (added in devenv 1.7, present in 2.0) form a directed acyclic graph executed in parallel; edges are declared with before/after. The key feature is content-aware incremental execution via execIfModified: a task is skipped if the listed files haven't changed. Tracking is by both mtime and content hash — if the timestamp changed but content didn't, the task is still skipped.

tasks."build:client" = {
  exec = "bun ./scripts/build-client.ts";
  execIfModified = [ "client/" "shared/" ];  # skip if untouched
};

For HyperIDE's oxc/tsgo monorepo this is a native build/lint/typecheck cache without a separate Turborepo/Nx. It doesn't match them feature-for-feature (no remote cache out of the box like Turbo/Nx Cloud — that's covered by Cachix), but locally a DAG + content-hash covers the typical "don't rebuild what didn't change" case.

2.5 git-hooks: declarative, with oxfmt confirmed 3-0

devenv has first-class pre-commit integration via the git-hooks.nix module (formerly pre-commit-hooks.nix; the backend recently migrated from pre-commit to the Rust-based prek). Hooks are declared in devenv.nix; the integration auto-enables as soon as any hook is configured. On shell entry, .git/hooks/pre-commit is installed automatically, and .pre-commit-config.yaml is a symlink into the Nix store (no need to commit it).

A direct hit on HyperIDE's toolchain. git-hooks.nix ships ready hooks for eslint, biome, prettier, denofmt and — importantly — oxfmt (with a configurable binPath). The formatter from the project's oxc toolchain is available as a declarative hook with no custom wrapper. (Initial web summaries wrongly claimed oxfmt was absent due to a truncated GitHub blob view; the raw modules/hooks.nix source disproved this.)

git-hooks.hooks = {
  oxfmt.enable = true;
  # oxlint and the tsgo typecheck — via a custom entry hook (see open questions)
};

2.6 Monorepo imports confirmed 3-0

devenv 1.10 (Oct 2025) added monorepo imports: each subdirectory carries its own devenv.nix/devenv.yaml and imports a centralized shared config. Paths starting with / resolve from the git repository root (where .git lives). The shared config centralizes packages, services and git-hooks, and packages inherit and extend them. This maps onto HyperIDE's layout (workspaces: ["packages/*"]): one shared base config plus per-package overrides.

2.7 CI in one command confirmed 3-0

The recommended two-step: hooks at commit time locally + devenv test in CI. devenv test builds the shell and runs all defined git-hooks against the whole repository (pre-commit only hits staged files — different scope, same definitions), plus enterTest and process start/stop. GitHub Actions integration uses standard composable actions:

# .github/workflows/ci.yml (fragment)
- uses: actions/checkout@v5
- uses: cachix/install-nix-action@v31
- uses: cachix/cachix-action@v16    # Nix binary cache → CI doesn't rebuild the env
  with: { name: devenv }
- run: nix profile add nixpkgs#devenv
- run: devenv test

4. devenv vs the current stack (bun + Docker)

For devenv

  • Nix-grade reproducibility — exact versions of all binaries, not just JS packages;
  • Runs natively on the host — no virtualization overhead (faster dev loop than Docker on macOS);
  • One declaration = packages + processes + services + hooks + CI;
  • First-class bun, an oxfmt hook, monorepo imports — hits the project's stack;
  • Cachix provides a binary cache — CI and fresh machines don't rebuild the env.

Against devenv

  • Requires Nix for everyone — steep learning curve, a new class of debugging problems;
  • Does not isolate the OS like Docker — devenv reproduces dependencies, not the kernel/distro; it doesn't replace Docker-based e2e;
  • On macOS the system Apple SDK breaks part of reproducibility (see §5);
  • 2.0 subsystems (Rust process manager, prek backend) are fresh — the API may not have settled;
  • The "<100ms activation" myth is refuted — there is no instant shell entry.

The key coexistence nuance. devenv and HyperIDE's Docker e2e are not interchangeable. Docker gives OS isolation for e2e (which devenv does not), while devenv gives a declarative environment and on-host process orchestration. The realistic scenario is that devenv complements the stack (managing the host toolchain and local dev processes) while Docker stays for e2e. Exactly how devenv processes coexist with the current Docker pipeline (port/resource contention) is not covered by the sources — it's the first thing to verify in a pilot.

6. Open questions for a pilot

  1. Coexistence with Docker e2e — does devenv replace, complement, or contend (ports/resources) with Docker orchestration of local services? The sources don't cover interaction with an existing pipeline.
  2. Real cold-entry speed into devenv shell on team machines (with and without Cachix) — there is no "instant" activation; a benchmark is needed.
  3. Teardown reliability under devenv up -d given the open issues — critical if e2e relies on clean shutdown of background services.
  4. oxlint and tsgo as hooks — git-hooks.nix ships oxfmt, but does it cover oxlint as a ready hook, and how easy is wrapping the tsgo typecheck in a custom shell hook to fully replace any husky/lint-staged setup?

7. Recommendation

A scoped pilot — yes; a wholesale migration — no. Technically devenv hits HyperIDE's stack accurately (bun, oxfmt, monorepo, dev-server orchestration). But the main cost is organizational, not technical: Nix for the whole team. A sensible path:

Phase 1 (1–2 days). One developer installs Nix + devenv, writes a devenv.nix with languages.javascript.bun, orchestration of scripts/dev.ts with an HTTP readiness probe, and an oxfmt hook. Measures cold/warm entry, checks process teardown, checks Docker-e2e port conflicts.

Phase 2 (only if Phase 1 lands). Monorepo imports for packages/*, devenv test in one CI job alongside the existing one, a Cachix cache. The decision on a full switch comes only from results — never upfront.

Do not: replace Docker e2e with devenv (different jobs), rely on "instant activation" (it doesn't exist), or roll it out to the whole team without measuring the Nix onboarding cost.
